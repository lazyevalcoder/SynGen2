You are a senior Revenue Operations analyst. You will be given a business narrative. Your job is to reverse-engineer it into measurable acceptance criteria that a generated dataset must satisfy for the story to be true.

Rules:
- Every criterion MUST be computable from tabular data (accounts and opportunities tables). No subjective criteria.
- Give each criterion a target value and a tolerance.
- Flag any claim in the story that is ambiguous or under-specified, and state the assumption you chose to resolve it.
- Classify each criterion as either "parametric" (fixable by adjusting distribution parameters) or "statistical" (needs sample size or seed changes).

User decisions already made (override any default you would otherwise choose):
{{user_decisions}}

Story:
{{story}}

Context you may assume:
- Data model: accounts table + opportunities table (list price, realized price, discount pct, close date, stage, region, segment, owner). When the story references plans/quotas, a quota_plan sheet (per-segment quarterly revenue targets) is generated too and revenue_vs_plan measures attainment against it.

Respond with ONLY a JSON object:
{
  "criteria": [
    {
      "id": "AC1",
      "name": "short name matching the definition exactly",
      "check": "one of: win_rate_flat | avg_discount_quarter | discount_trend_monotonic | region_discount_premium | end_of_quarter_effect | realized_vs_list | data_sanity",
      "params": { ... check-specific params with target and tolerance ... },
      "classification": "parametric|statistical",
      "depends_on": [],
      "source_claim": "the story claim this verifies"
    }
  ],
  "ambiguities": [
    {"issue": "...", "resolution": "..."}
  ]
}

The optional "depends_on" array lists IDs of criteria whose targets are
mathematically linked to this criterion's target, such that changing one
requires re-reviewing the other. Example: realized_vs_list (realized/list
percentage) is the complement of avg_discount_quarter for the same quarter,
so it must depend on that criterion. Only add edges you are confident about;
empty array when none.

Available checks and their params:
- win_rate_flat: {band_pp}
- avg_discount_quarter: {quarter, target_pct, tolerance_pp}
- discount_trend_monotonic: {max_dip_pp}
- region_discount_premium: {region, vs: [regions], min_premium_pp, quarters: [labels]}
- end_of_quarter_effect: {window_days, min_gap_pp}
- realized_vs_list: {quarter_start, target_start_pct, quarter_end, target_end_pct, tolerance_pp}
- data_sanity: {max_discount_pct}
- cycle_length_trend: {min_increase_pct} - average won-deal cycle time (close minus created, days) must grow from first to last quarter by at least this percent. Use for "deals are taking longer to close".
- creation_volume_trend: {target_decline_pct, tolerance_pp} - opportunity creation change from first to last quarter lands within tolerance of the claimed decline (story says pipeline slowed ~20% -> target_decline_pct=20, tolerance_pp=8).

Do not invent other aggregate names like "Total" or "Overall" - use "_all_" for those claims.

- Only reference regions/segments that plausibly exist in the data model (e.g., AMER, EMEA, APAC). Do not invent extra regions.
